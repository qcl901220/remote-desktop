# 06 — 和商业产品的差距 & 改进方向

## 前言

这个项目的目的是**学习原理**，不是做一个可以替代向日葵/RustDesk 的产品。

这篇文档诚实讲我们和商业产品的差距在哪里——这些差距恰恰是深入学习的方向。

## 差距一览

| 维度 | RemoteDesk (本项目) | 商业产品 |
|------|-------|---------|
| 编码 | JPEG 逐帧压缩 | H.264/H.265 视频编码 |
| 传输 | WebSocket (TCP) | WebRTC (UDP, P2P) |
| NAT 穿透 | ❌ 仅局域网/VPN | ✅ STUN/TURN/ICE |
| 音频 | ❌ | ✅ |
| 安全 | HMAC 认证，明文传输 | TLS + 端到端加密 |
| 捕获 | CPU (mss + Pillow) | GPU 硬件编码 |
| 自适应 | 手动调画质 | 自适应码率 |
| 平台 | 仅 Windows 被控 | 全平台 |
| 剪贴板 | 纯文本 | 文本 + 图片 + 文件 |
| 输入 | 键鼠 + 中文 IME (compositionend) | 原生输入法透传/手柄/触控 |
| 锁屏 | ❌ 锁屏后无法操作 | ✅ 系统服务级输入注入 |

## 差距详解

### 1. JPEG vs H.264 — 最大的性能差距

**我们的方案**：每帧独立 JPEG 压缩

```
帧1: [完整 JPEG]  →  100KB
帧2: [完整 JPEG]  →  100KB  （即使只有一个光标在闪）
帧3: [完整 JPEG]  →  100KB
```

**H.264 的方案**：帧间预测

```
I帧: [完整帧]     →  100KB
P帧: [只编码变化]  →  2KB   （光标闪了一下，只传那几个像素的差异）
P帧: [只编码变化]  →  2KB
...
I帧: [完整帧]     →  100KB  （每隔 N 帧刷新一次完整画面）
```

H.264 的压缩比是 JPEG 的 **10-50 倍**。这就是为什么向日葵可以在 1Mbps 的网络上流畅运行，而我们需要 3-5Mbps。

**改进方向**：
- 用 `ffmpeg` 子进程做 H.264 编码（中等难度）
- 用 GPU 硬件编码器 NVENC/QSV（高难度）
- 用 WebRTC 的 MediaStream（换架构）

### 2. WebSocket (TCP) vs WebRTC (UDP) — 延迟

TCP 保证数据可靠到达——但代价是：如果一个包丢了，后面所有包都要等它重传。

```
TCP:  帧1 帧2 [丢失] 帧3 帧4 ← 帧3、帧4 被阻塞，等重传
      结果：卡顿 200ms

UDP:  帧1 帧2 [丢失] 帧3 帧4 ← 帧3、帧4 正常到达，丢的帧不管了
      结果：画面闪一下但不卡
```

对于远程桌面：**丢一帧比卡一下好得多。** 这就是为什么商业产品用 UDP（WebRTC）。

**改进方向**：
- 在 Python 端用 `aiortc` 实现 WebRTC
- 需要一个信令服务器做连接协商
- 复杂度会增加 3-5 倍

### 3. NAT 穿透 — 最大的功能差距

这是"局域网工具"和"互联网工具"的根本区别。

```
你的家里电脑 ─┐                    ┌─ 公司电脑
  192.168.1.x  │   互联网（NAT）    │  10.0.0.x
               ├──── ? ─────────────┤
               │  双方都在 NAT 后面  │
               │  互相看不到对方     │
```

向日葵/RustDesk 的解决方案 — **ICE 框架**：

1. **STUN**：问一个公网服务器"我的公网 IP 是什么？"，双方交换公网地址
2. **打洞**：双方同时向对方的公网地址发包，尝试在 NAT 上打开通道
3. **TURN**：如果打洞失败（对称 NAT），通过公网中继服务器转发

向日葵收费的本质就是这个 TURN 中继服务器的成本——免费用户限速就是限制中继带宽。

**改进方向**：
- 自建 coturn 服务器（开源 TURN 实现）
- 但这就需要一台公网服务器，违背了"零第三方依赖"的初衷

### 4. 传输加密

我们只做了认证（密码不明文传输），但认证后的数据流是明文的。

```
当前：  认证 ✅ → [明文 JPEG 帧] [明文键盘事件]
应有：  认证 ✅ → [TLS 加密的 JPEG 帧] [TLS 加密的键盘事件]
```

**改进方向**：
- WebSocket 加 TLS → WSS（需要证书）
- 自签证书 + 首次信任模式（类似 SSH）

### 5. 音频转发

远程桌面不传声音，会议/演示场景就不好用。

**改进方向**：
- Windows 上用 WASAPI Loopback 捕获系统音频
- 编码成 Opus 或 AAC
- 通过 WebSocket 或 WebRTC 音轨传输

## 总结：学习路线图

如果你想继续深入，建议按这个顺序：

```
当前 ──→ H.264 编码 ──→ WebRTC ──→ NAT 穿透 ──→ 音频
 (JPEG)    (性能飞跃)    (架构升级)   (可达性)     (功能完整)
  ⭐         ⭐⭐         ⭐⭐⭐       ⭐⭐⭐⭐      ⭐⭐
```

每一步都会让你学到不同领域的知识：图像/视频编码、网络协议、NAT 与防火墙、音频处理。

这也正是这个项目作为学习项目的价值——它不是终点，而是起点。
